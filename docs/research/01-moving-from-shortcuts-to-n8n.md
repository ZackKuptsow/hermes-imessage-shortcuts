# Put n8n behind Shortcuts, not in its place

The inbound text path can move "to n8n" within every standing rule, but only if n8n takes the relay and orchestration role and leaves detection where it is: the Shortcuts "Message" automation is the one ingress on this Mac that needs no privacy grant at all and filters by sender before the text leaves Messages, so the compliant design keeps it as the trigger and points it at an n8n Webhook node on 127.0.0.1 instead of the plugin's listener. Every route that would let n8n notice texts itself either puts Full Disk Access on n8n's own process (a `sqlite3` poll, the paid Apple Messages node), listens on the LAN and forwards every household text (BlueBubbles), or is a hosted vendor; the single exception, an `imsg watch` sidecar under launchd, passes only because the sidecar alone holds Full Disk Access and n8n cannot reach it. On the Hermes side the surface to call is the **API server on 127.0.0.1:8642** (`/p/<profile>/v1/chat/completions` with a per-sender `X-Hermes-Session-Id`, or `/v1/runs` plus polling), the only surface that returns the answer to the caller, which is what lets n8n send the reply through `imsg` from an Execute Command node. That last step forces a **native `npm` install of n8n 2.x**, and n8n declared that path unsupported in 3.0 (beta 27 Oct 2026, stable targeted early December) with 2.x getting security and critical fixes for twelve months afterwards; a Docker n8n can run the relay but cannot reach Messages.app. The plugin's guards split three ways under this design: the secret header, loopback bind and per-sender session are rebuilt in n8n and config; the exact-two-toolset pin moves to `platform_toolsets.api_server` and loses its startup refusal unless re-implemented as a pre-flight against `GET /v1/toolsets`; the five-command allowlist disappears as slash commands and becomes three API calls. Message text stays out of n8n's SQLite only with `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` and `EXECUTIONS_DATA_SAVE_ON_ERROR=none`, and off the network only with diagnostics, version checks and templates switched off. n8n is **fair-code under the Sustainable Use License, not OSI open source**; personal self-hosting is explicitly permitted, and Node-RED (Apache-2.0) is the nearest OSI-licensed tool that also runs natively with a shell node. The cheapest first step, n8n as a pure relay between Shortcuts and the unchanged plugin, loses no guard, needs no Execute Command, and is the right place to learn n8n before deciding whether to move the Hermes call at all.

## Only two of five ingress routes keep the Messages database closed

Every way of noticing a new iMessage on a Mac is either Apple's own Shortcuts trigger, which Messages evaluates and hands over one request at a time, or a reader of `~/Library/Messages/chat.db`, which macOS protects behind Full Disk Access granted to the executable that opens it; `imsg` itself documents that when it is launched indirectly "the parent process needs the grant, not the terminal you opened" ([imsg permissions](https://raw.githubusercontent.com/openclaw/imsg/main/docs/permissions.md)). Apple's own engineers confirm the mechanism: TCC "tracks access through code-signing properties of the executable", so the poster who ran a Node script had to grant Full Disk Access to `/usr/local/bin/node`, after which "every Node script on the machine then has FDA" ([Apple Developer Forums](https://developer.apple.com/forums/thread/760291)). Because the second household member's texts sit in the same database, the detector role can be held only by Shortcuts, which holds nothing, or by a process n8n can never invoke.

| Route | Permission needed | Process that holds it | Sender filtered before the text leaves Messages? | Rule status |
|---|---|---|---|---|
| **A. Shortcuts Message automation posting to an n8n Webhook node** | None | None; n8n holds nothing | Yes, the trigger's Sender filter runs before the shortcut starts ([MacMost](https://macmost.com/an-introduction-to-shortcuts-automation-in-macos-tahoe.html)) | Passes every rule |
| **B. `imsg watch --json --participants <handle>` as a launchd sidecar pushing to n8n** | Full Disk Access on the sidecar only | The executable named in the LaunchAgent plist | No; the filter runs inside `imsg` after the row is read, so the sidecar sees every household text ([imsg watch](https://raw.githubusercontent.com/openclaw/imsg/main/docs/watch.md)) | Passes only if n8n cannot reach the sidecar and never holds Full Disk Access itself |
| **C. BlueBubbles server webhook** | Full Disk Access plus Automation plus Contacts in one process ([BlueBubbles docs](https://docs.bluebubbles.app/server/llms-full.txt)) | BlueBubbles Server.app | No; webhooks fire for every message, filtering is downstream ([n8n-nodes-bluebubbles](https://github.com/ejlevin1/n8n-nodes-bluebubbles)) | Fails: listens on LAN port 1234 with no documented loopback bind, and every household text reaches n8n |
| **D. npm community nodes** (Photon, Blooio hosted; a paid Gumroad node) | Hosted vendor, or Full Disk Access on n8n ([Gumroad listing](https://littledivy.gumroad.com/l/imessage-n8n-node)) | A third party's cloud, or n8n's own process | Unknown or no | Fails at least one rule each |
| **E. `sqlite3 chat.db` poll from an n8n Execute Command node** | Full Disk Access on n8n's responsible executable | `node`, and therefore every workflow and child command | No; the whole table is readable | Fails the gateway rule and the household rule; also unreliable because `text` is NULL for many rows with the body in `attributedBody` ([imsg issue 249](https://github.com/openclaw/imsg/issues/249)) |

Route A is the current design with one hop replaced. On the n8n side the Webhook node offers Header Auth through a Webhook credential, an **IP allowlist** that returns 403 to anything not on it, and a "Respond Immediately" mode that returns "Workflow got started." before the workflow runs, so the Shortcut's HTTP call returns in milliseconds and never waits on the agent ([n8n Webhook node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)). Two details matter for parity with the plugin. First, the Webhook node's header check lowercases the header name but compares the value with `!==`, an exact and non-timing-safe comparison, and it reads the body before authenticating ([Webhook utils.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/Webhook/utils.ts)); the plugin today compares in constant time and reads a body only after the secret matches ([plugin README](../../../README.md)). On a loopback-only listener with a long random value this is a tolerable loss, not a free one. Second, the request must carry `Content-Type: application/json` for n8n to parse the body as JSON ([n8n Webhook common issues](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/common-issues/)), which the Shortcut already sends.

Route B is the fallback if Shortcuts proves flaky, and it is far heavier than it looks. The LaunchAgent must name `/opt/homebrew/bin/imsg` (or a compiled wrapper) directly as its program, because a `/bin/zsh` wrapper script would make `zsh` the executable holding Full Disk Access; the grant goes stale after Homebrew or macOS updates and must be toggled off and on ([imsg troubleshooting](https://raw.githubusercontent.com/openclaw/imsg/main/docs/troubleshooting.md)). A bare `imsg watch` starts at the tail and "Earlier messages aren't replayed", so anything that arrives while the sidecar is down is lost unless the sidecar persists the last rowid and replays through `--since-rowid` or the RPC `messages.after` cursor, which is exactly the bug OpenClaw hit and fixed in May 2026 ([imsg watch](https://raw.githubusercontent.com/openclaw/imsg/main/docs/watch.md); [openclaw issue 78649](https://github.com/openclaw/openclaw/issues/78649)). Since v0.19.1 the `--participants` filter also matches the account's own outbound messages in a 1:1 chat, so the sidecar must drop `is_from_me` events before posting ([imsg releases](https://github.com/openclaw/imsg/releases)). And the design question the research left open is the one that decides compliance: the plist carrying the `--participants` value is user-writable, and an n8n workflow runs as the same user, so "n8n cannot reach the sidecar" has to be made true by something other than file permissions.

Shortcuts itself is not beyond doubt. No 2025 to 2026 report of the Message trigger failing on macOS 26.x was found, but the Mail trigger in the same release train did stop working on 26.2 betas ([MacScripter](https://www.macscripter.net/t/changes-to-the-shortcuts-app-in-tahoe/77180)), which is evidence that Apple ships broken automation triggers in point releases. The practical consequence is a heartbeat, such as a scheduled self-text that must produce an n8n execution, rather than trust.

## n8n's 3.0 Docker turn puts the native install on a twelve-month clock

The reply leg is where n8n's own roadmap collides with the Mac. n8n's stable line on 30 Oct 2026 is **2.45.7**, with minors weekly and patches almost daily ([GitHub releases](https://github.com/n8n-io/n8n/releases)). Three days earlier n8n released **3.0.0 beta**, with stable targeted for "early December" 2026, and the announcement states that installing with `npm` or `npx n8n` "is no longer supported", that self-hosted n8n "now runs on Docker", that the upgrade is one-way with no rollback, and that after stable the 2.x line gets "security and critical bug fixes for 12 months" ([Introducing n8n v3](https://blog.n8n.io/introducing-n8n-v3)). The breaking-changes page is blunter: "Self-hosted n8n requires a Docker-based deployment" ([v3.0 breaking changes](https://docs.n8n.io/changelog/v30-breaking-changes)). There is no Homebrew formula to fall back on; `formulae.brew.sh/formula/n8n` returns 404 ([Homebrew formulae](https://formulae.brew.sh/formula/n8n)).

Docker cannot do this job. The Execute Command node's own documentation says that with Docker "the command runs inside the n8n container, not on the Docker host" ([Execute Command node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executecommand/)), and Docker Desktop's host networking is a layer-4 TCP/UDP bridge for Linux containers, not a way to send Apple Events ([Docker host network driver](https://docs.docker.com/engine/network/drivers/host/)). The only Docker layout that could send a text is a small native HTTP service on the Mac that accepts a request from the container via `host.docker.internal` and runs `imsg` ([Docker Desktop networking](https://docs.docker.com/desktop/features/networking/networking-how-tos/)), which is a third process holding the Automation grant and whose reachability on a strictly `127.0.0.1`-bound socket from a container is not stated in any Docker page read.

So a native `npm install -g n8n@2.45.x` is the only install that can call `imsg`, and it is viable on this Mac despite a stale documentation line. The npm page still says n8n "requires a Node.js version between 20.19 and 24.x, inclusive" ([Install with npm](https://docs.n8n.io/hosting/installation/npm/)), but `package.json` at the 2.45.7 tag declares `engines.node` as `>=24.0.0` ([package.json at n8n@2.45.7](https://raw.githubusercontent.com/n8n-io/n8n/n8n@2.45.7/package.json)) and the official image builds `FROM node:26.12.1-alpine3.24` ([Dockerfile at n8n@2.45.7](https://raw.githubusercontent.com/n8n-io/n8n/n8n@2.45.7/docker/images/n8n/Dockerfile)). The Mac's Homebrew Node 26.10.0 satisfies the code; the runtime n8n actually tests is 26.12.1. The planning horizon that follows is concrete: feature updates on npm stop at 3.0, security fixes run to roughly **December 2027**, and anything built now should assume a later move to Docker-plus-sidecar or to another tool.

Re-enabling the node is its own trap. Execute Command is "disabled by default from n8n 2.0" through `NODES_EXCLUDE`, whose default is `["n8n-nodes-base.executeCommand", "n8n-nodes-base.localFileTrigger"]` ([Nodes env vars](https://docs.n8n.io/hosting/configuration/environment-variables/nodes/)). The one issue that tried `N8N_NODES_INCLUDE=n8n-nodes-base.executeCommand` got nothing; the maintainer's answer was `NODES_EXCLUDE="[]"` ([n8n-io/n8n#23439](https://github.com/n8n-io/n8n/issues/23439)). A tighter form is an explicit exclude list that drops `executeCommand` but keeps `localFileTrigger`, `readWriteFile`, `ssh` and `git` excluded; nothing in the docs enumerates every command-capable node, so that list is reasoned, not official. The node hands the whole command string to `spawn(command, { shell: true })`, which on Unix means `/bin/sh`, not the zsh the docs example shows; it does no escaping, writes no stdin, has no timeout, and throws on non-zero exit with stderr as the message ([ExecuteCommand.node.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/ExecuteCommand/ExecuteCommand.node.ts); [Node.js child_process](https://nodejs.org/api/child_process.html)). An expression like `imsg send --to {{ $json.to }} --text {{ $json.text }}` therefore turns any message containing `"`, `$(`, a backtick or `;` into shell syntax. The safe pattern is to keep user text off the command line entirely: base64-encode the body in a Set node (the base64 alphabet has no shell metacharacters) and decode it inside a fixed command, rather than writing it to a temp file, which would put message text on disk.

Running it unattended has no official recipe. No docs.n8n.io or forum page documents launchd; the one Mac mini thread establishes that launchd ignores `.env` files, that every `N8N_*` variable must live in the plist's `EnvironmentVariables` dictionary (with `NODES_EXCLUDE` as the literal string `[]`), and that the internal task runner inherits the main process environment ([community.n8n.io 296105](https://community.n8n.io/t/enabling-built-in-library-in-code-node-and-execute-command-node/296105)). The unit must be a user LaunchAgent, not a LaunchDaemon, because an agent without `LimitLoadToSessionType` runs in the GUI login session ([Apple Developer Forums](https://developer.apple.com/forums/thread/696859)) and Apple Events to Messages need that session. The Automation prompt names the application sending the events, not the script ([Scripting OS X](https://scriptingosx.com/2020/09/avoiding-applescript-security-and-privacy-requests/)), and permissions are attributed to the responsible process, which for a bare executable started by launchd is that executable ([Qt blog](https://www.qt.io/blog/the-curious-case-of-the-responsible-process)); so the grant lands on the `node` binary, which means every n8n workflow, not just this one, can then drive Messages, and a Node upgrade that changes the binary will prompt again. Nobody has published the exact prompt text for `node` under launchd on macOS 26; that is a test, not a lookup.

Memory fits the 3 GB budget with room. n8n's official sizing puts an idle Cloud instance "at about 100MB" and plans for "320 MB - 2 GB", calling n8n "not CPU intensive" ([Embed prerequisites](https://docs.n8n.io/embed/prerequisites/)); the 800 MB to 2 GB idle figures in forums come from Linux cloud deployments in queue mode with a worker and Redis ([community.n8n.io 107104](https://community.n8n.io/t/railway-setup-taking-up-2gb-of-ram-even-in-idle/107104)). A single-user regular-mode instance is the main process plus one internal runner, and both can be capped (`NODE_OPTIONS=--max-old-space-size`, `N8N_RUNNERS_MAX_OLD_SPACE_SIZE`) ([Task runner env vars](https://docs.n8n.io/hosting/configuration/environment-variables/task-runners/)). No Apple-silicon measurement exists, and the internal runner mode "is deprecated as of n8n 3.0" with a startup warning in 2.x, which is harmless on this timeline ([Set up task runners](https://docs.n8n.io/hosting/configuration/task-runners/)). Docker Desktop's own VM footprint was not measured by the research, which is one more reason the native path is the lighter one on paper and an unmeasured one in practice.

## The API server is the surface to call, and the plugin's guards split three ways

Hermes v0.22.5 offers five ways for n8n to hand over a text, and only two of them give the answer back. The **API server** returns `choices[0].message.content` synchronously on `POST /v1/chat/completions`, or 202 plus a run id on `POST /v1/runs` for polling or SSE; it binds **127.0.0.1:8642 by default**, refuses to start without a Bearer `API_SERVER_KEY` of at least 16 characters, and under `/p/<profile>/` demands that profile's own key, failing closed if the profile has none ([Hermes API server docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server); [api_server.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/api_server.py#L219)). Hermes's own decision guide names it for "a language-agnostic HTTP client, or curl-driven automation" ([programmatic-integration.md](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/website/docs/developer-guide/programmatic-integration.md#L225)). The **webhook adapter** is receipt-only: an agent-mode route answers 202 `{"status":"accepted"}` and can deliver only to `log`, a GitHub comment or a connected messaging platform, never to an HTTP URL or back to the caller ([Hermes webhooks docs](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/webhooks); [webhook.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/webhook.py#L741)); the upstream `http_callback` request that would change this has sat at `needs-decision` since July ([hermes-agent issue 4386](https://github.com/NousResearch/hermes-agent/issues/4386)), and a third-party n8n guide claiming the adapter returns the agent's reply in the HTTP body is contradicted by the source. It also keys every session on the delivery id and binds **all interfaces by default** with no `WEBHOOK_HOST` variable, so it fails the per-sender-session need and needs `platforms.webhook.host: 127.0.0.1` pinned by hand ([webhook.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/webhook.py#L60)). **Outbound hooks** can deliver the final answer to an n8n URL via `post_llm_call`, but the same POST carries `user_message` and the full `conversation_history`, and the hook does not fire on interrupted or budget-exhausted turns ([hooks.md](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/website/docs/user-guide/features/hooks.md#L457)), which makes it the surface most at odds with the no-logging rule. **`hermes chat -q`** is now a thin client that attaches to the gateway over a local WebSocket, with sessions reusable by title but CLI-owned, with CLI toolset defaults and toolsets frozen at creation ([cli.md](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/website/docs/user-guide/cli.md#L176)). The **plugin adapter** remains the one surface where a per-sender session, a per-source toolset pin and a command allowlist all exist natively ([base.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/base.py#L4831)).

If n8n is to own the conversation, the call is `POST http://127.0.0.1:8642/p/<texting-profile>/v1/chat/completions` with `Authorization: Bearer <that profile's key>` and `X-Hermes-Session-Id: <opaque per-sender token>`. The header is what makes "one session per sender" possible: without it the session id is derived from the system prompt plus the first user message, so every new text would open a new session ([api_server_openai_routes.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/api_server_openai_routes.py#L859)). The token must not be the handle, because the session id is the one identifier that reaches a log line, on a failed history load ([api_server_openai_routes.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/api_server_openai_routes.py#L888)). API sessions cannot bind sessions the plugin created; such a request is refused with 409 `permission_denied`, so the household's existing threads restart once ([Hermes API server docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)). Timeouts are n8n's problem to own: no wall clock bounds a synchronous turn in `api_server.py` below the agent's 600-second liveness watchdog ([config_defaults.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/hermes_cli/config_defaults.py#L293)), the n8n HTTP Request node's UI default timeout is **10,000 ms** with a runtime fallback of 300,000 ms when unset ([HttpRequest Description.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/HttpRequest/V3/Description.ts)), and the local model's turn length is not in any source. `/v1/runs` plus a Wait-and-poll loop is the shape that escapes the client timeout entirely.

| Guard the plugin enforces today ([plugin README](../../../README.md)) | Where it lives in the n8n plus API server design | Verdict |
|---|---|---|
| Shared secret, at least 32 characters, compared in constant time before the body is read | Shortcuts to n8n: Webhook Header Auth, exact non-timing-safe compare, 403 on mismatch. n8n to Hermes: Bearer key, `hmac.compare_digest`, at least 16 characters ([api_server.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/api_server.py#L1481)) | Rebuilt; weaker on the first hop |
| Listener binds 127.0.0.1 or ::1 and refuses any other address | `N8N_LISTEN_ADDRESS=127.0.0.1` (n8n's default is `::`, all interfaces) ([Deployment env vars](https://docs.n8n.io/hosting/configuration/environment-variables/deployment/)); API server defaults to 127.0.0.1 | Rebuilt; n8n's default is the wrong one |
| Sender allowlist in a file and an env var that must agree; off-list senders dropped before the gateway; sends to off-list handles refused | Shortcuts' Sender filter plus an IF node in n8n against a stored list before both the Hermes call and the `imsg` command; Community edition has no `$vars`, so the list lives in a credential or a Set node ([Community edition features](https://docs.n8n.io/hosting/community-edition-features/)) | Rebuilt in workflow JSON; the two-source agreement check is lost |

| Slash commands limited to `/new`, `/reset`, `/stop`, `/approve`, `/cancel`; anything else reaches the model as words | The API server never calls `handle_message()`, so no text is a command: `/new` and `/reset` become a fresh session id or `DELETE /api/sessions/{id}`; `/stop` becomes `POST /v1/runs/{id}/stop` (runs only); `/approve` becomes `POST /v1/runs/{id}/approval` (runs or streaming only) ([api_server.py](https://github.com/NousResearch/hermes-agent/blob/v0.22.5/gateway/platforms/api_server.py#L2289)) | Replaced by three API calls; the `/new` confirmation that `/approve` and `/cancel` served today disappears |

The pattern in the table is that guards written as a few lines of tested Python become either configuration keys that nothing re-checks or workflow JSON that is reviewed by eye. The toolset guard is the sharpest case: today the adapter asks Hermes's own resolver which toolsets it would enable and refuses to listen if the answer is wider than two, on every text ([plugin README](../../../README.md)); the API server has nothing comparable, and `GET /v1/toolsets` is the only place the effective list can be read at runtime ([Hermes API server docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)). Whether the plugin-registered `imessage_shortcuts` toolset even resolves for the `api_server` platform is one of the things that call must confirm before the design is trusted.

### A relay-first step keeps every guard while n8n is learned

There is a shape with none of these losses: Shortcuts posts to the n8n Webhook node, and an HTTP Request node forwards `{sender, sent_at, text}` with the `X-Hermes-Secret` header, held as an n8n credential, to the unchanged plugin on 127.0.0.1:8645. Every guard stays in the plugin, where it already runs; n8n needs no Execute Command, no Automation grant and no `NODES_EXCLUDE` change; and because n8n never touches `imsg`, a Docker install would work in principle, subject to the unverified question of whether a container's connection to `host.docker.internal` reaches a `127.0.0.1`-bound socket. The cost is that the text now transits n8n, so the retention settings below are mandatory from day one, and there are two secrets to keep instead of one. For an owner whose goal is to learn n8n, this is the step that teaches the data model, expressions, credentials and error workflows on a live but harmless path, and it leaves the decision to move the Hermes call until the API server's guards have been rebuilt and tested.

## Two switches keep texts out of SQLite, three keep n8n off the network

By default n8n writes the full input and output of every production execution, successful or failed, to its SQLite database and keeps it for **336 hours** with a 10,000-row cap pruned hourly ([Executions env vars](https://docs.n8n.io/hosting/configuration/environment-variables/executions/)). In this workflow the message text is the Webhook node's `json.body` and, on the reply leg, the Execute Command node's command string, so with defaults both are persisted on every run. `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` and `EXECUTIONS_DATA_SAVE_ON_ERROR=none`, with `EXECUTIONS_DATA_SAVE_MANUAL_EXECUTIONS=false`, stop that; the docs' recommended compromise of saving errors only would still store the text and the `imsg` command line for every failure ([Execution data](https://docs.n8n.io/hosting/scaling/execution-data/)). The feature that would hide saved data without deleting it, execution-data redaction, is Enterprise-only and leaves "Data in the database unchanged" anyway ([Redact execution data](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/redact-execution-data.md)). Insights keeps counting production executions on all editions; `N8N_DISABLED_MODULES=insights` turns even the count off ([Insights](https://docs.n8n.io/administer/observe-and-log/track-usage-with-insights.md)). Pruned rows on SQLite do not free disk space without a vacuum ([Execution data](https://docs.n8n.io/hosting/scaling/execution-data/)).

n8n's own logger is clean at the default level. The webhook request handler's seven log calls reference execution ids, workflow names and `responseMode`, never `req.body` or `req.headers`, with one line that interpolates an unsanitised `error.message` ([webhook-helpers.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/cli/src/webhooks/webhook-helpers.ts)). The Execute Command node turns a non-zero exit into a `NodeOperationError` whose message is stderr ([ExecuteCommand.node.ts](https://raw.githubusercontent.com/n8n-io/n8n/master/packages/nodes-base/nodes/ExecuteCommand/ExecuteCommand.node.ts)), and that message is what an Error Trigger receives, so an error workflow must forward only the workflow name, execution id and exit code. Telemetry is on by default, sends "an instance pulse" every six hours ([Control telemetry](https://docs.n8n.io/hosting/securing/telemetry-opt-out/)), and collects workflow shape, error messages that "can sometimes include text from your workflow, such as a node name", and "the registrable domain of HTTP Request addresses and webhook calls", though "not the data that flows through your workflows" ([n8n privacy](https://docs.n8n.io/privacy-and-security/privacy.md)). The isolation page names the three switches and the three config values to blank ([Isolate n8n](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/isolate-n8n.md)); what it does not cover is whether an unregistered Community instance ever contacts `license.n8n.io`, whose auto-renew defaults to on ([License env vars](https://docs.n8n.io/hosting/configuration/environment-variables/licenses/)), so an egress check after first start is the only way to close that.

## Fair-code is not OSI, and Node-RED is the nearest licensed-open substitute

n8n describes itself as "fair-code distributed under the Sustainable Use License and n8n Enterprise License" ([n8n README](https://raw.githubusercontent.com/n8n-io/n8n/master/README.md)). The SUL v1.0 permits use and modification "for internal business purposes or for non-commercial or personal use" and distribution "only free of charge for non-commercial purposes"; files with `.ee.` in the name are excluded and require an Enterprise licence in production ([LICENSE.md](https://raw.githubusercontent.com/n8n-io/n8n/master/LICENSE.md); [LICENSE_EE.md](https://raw.githubusercontent.com/n8n-io/n8n/master/LICENSE_EE.md)). The FAQ names "personal projects, learning, research" as allowed and hosting n8n for clients, white-labelling or forking a competitor as not ([License FAQ](https://docs.n8n.io/n8n-community-license/community-license/license-faq.md)). Fair-code's own site says it "is not a software license" but a model for software that is free to use and source-available yet "commercially restricted by its authors", and it makes no claim of OSI approval ([faircode.io](https://faircode.io/)). For one person on one Mac the licence imposes no practical constraint; the Community-edition gaps that touch this project are the absence of custom variables, Git source control, execution redaction and workflow history beyond 24 hours ([Community edition features](https://docs.n8n.io/hosting/community-edition-features/)). Workflows-as-code is still possible: `n8n export:workflow --backup --output <dir>` writes one pretty-printed JSON per workflow and `import:workflow --separate` restores them, though n8n says it plans to deprecate the server CLI export with no date set ([CLI commands](https://docs.n8n.io/hosting/cli-commands/); [Export and import](https://docs.n8n.io/build/manage-workflows/export-and-import.md)).

If the open-source preference is firm rather than soft, the alternatives sort themselves by whether they run natively on macOS with a shell step. **Node-RED** is Apache-2.0, installs with `npm install -g node-red`, has an Exec node, and needs `uiHost` set to `127.0.0.1` in `settings.js` because it listens on all IPv4 interfaces by default ([node-red/node-red](https://github.com/node-red/node-red); [Node-RED configuration](https://nodered.org/docs/user-guide/runtime/configuration)); it is the closest like-for-like. **Huginn** is MIT, runs natively under Ruby, and its `ShellCommandAgent` runs only when `ENABLE_INSECURE_AGENTS` is `"true"` ([huginn/huginn](https://github.com/huginn/huginn); [shell_command_agent.rb](https://raw.githubusercontent.com/huginn/huginn/master/app/models/agents/shell_command_agent.rb)). **Kestra** has an Apache-2.0 core with a separate Enterprise Edition, runs as a standalone JAR on a JVM, and lists Shell among its scripting languages ([kestra-io/kestra](https://github.com/kestra-io/kestra); [Kestra standalone server](https://kestra.io/docs/installation/standalone-server)). **Windmill** (AGPLv3 core), **Activepieces** (MIT community edition with a commercial `packages/ee`) and **Automatisch** (AGPL-3.0 with `.ee.` files) all document Docker first, which brings back the Messages.app problem ([windmill-labs/windmill](https://github.com/windmill-labs/windmill); [activepieces/activepieces](https://github.com/activepieces/activepieces); [automatisch/automatisch](https://github.com/automatisch/automatisch)). For learning n8n specifically, the official courses moved to learn.n8n.io with a four-course 2026 sequence ([n8n Academy](https://learn.n8n.io/)), and the docs' "Understand key concepts" cluster on data structure, expressions, item linking and executions is the model-first reading ([n8n docs](https://docs.n8n.io/)).

## Conclusion

The research reframes the question. "Move the inbound path to n8n" cannot mean "let n8n detect texts", because detection on this Mac is a privilege and the rules assign it to nobody n8n can reach; it can only mean "let n8n carry the text between Apple's trigger and Hermes and, optionally, carry the answer back out". Once stated that way, the two shapes rank themselves. The relay-first shape changes nothing about the trust model, keeps every guard in the code that already enforces it, and survives n8n's own future (Docker-only 3.x, or a switch to Node-RED) because n8n never holds a privilege in it. The orchestrator shape buys a visible workflow at the cost of moving the sharpest guard, the exact-two-toolset refusal, from a per-text check in Python to a configuration key that a future Hermes migration can silently widen, and it ties the reply leg to a native n8n 2.x install whose feature life ends in December and whose security life ends a year later.

The durable version of this design therefore keeps privileged actions, sending through `imsg` and pinning toolsets, inside Hermes-side code, and gives n8n the role it can lose without consequence. If the orchestrator shape is still wanted after learning n8n on the relay, the two things to build before anything else are the `GET /v1/toolsets` pre-flight that replaces the startup refusal and the base64 command pattern that keeps message text out of `/bin/sh`; everything else in the guard table is configuration, and configuration is what the thirteen tests above exist to verify from a clean state.
